# 版本与升级规范

## 命名

产品显示 **K⁺-SESSION 1.0**，完整版本号 **1.0.0**，发布标签使用 **v1.0.0**。版本号不是部署地址，也不是数据编号。

| 后续变化 | 版本示例 |
| --- | --- |
| 向后兼容的问题修复 | 1.0.1 |
| 向后兼容的新功能 | 1.1.0 |
| 不兼容的接口、配置或升级要求变化 | 2.0.0 |

采用[语义化版本](https://semver.org/lang/zh-CN/)表达兼容程度；实际能否升级仍必须依据该次迁移说明和测试结果，不根据版本数字猜测。

## 源码、测试和发布的区别

- 开发分支保存正在修订的代码；本项目使用 codex/ 前缀。
- CI 是实际执行测试与构建的记录，可在没有 PR 时运行。
- PR 是提交修改供审查、准备合并的记录，不是测试是否执行的判断依据。
- main 是仓库默认展示的主分支。把已审查版本合并进去，不会自动在任何电脑安装或更新系统。
- Release 是面向使用者的版本说明和下载页，绑定明确标签和提交；安装包、SHA256和升级说明应与该版本一致。

参考：[GitHub PR](https://docs.github.com/en/pull-requests/reference/pull-requests)、[GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)。

## 每次更新

1. 在开发分支修改受影响模块，明确兼容范围和版本号。
2. 同步 package.json、package-lock.json 根记录、打包清单与更新记录；依赖版本不能混改。
3. 运行适用回归和安装/启动/数据保留验证，检查角色页面及关联模块。
4. 完成审查并获发布授权后合并 main，建立新的版本标签及 Release。
5. 发布已测试的安装包、校验值、变更和升级说明；**不覆盖**已发布的旧版本包或复用旧标签冒充新版本。

## 安装者升级

- 不会自动从 GitHub 拉取更新，不会自动迁移或上传使用者的数据。
- 升级前停止服务，完整备份安装目录，核对目标版本是否明确支持当前实例结构。
- 当前安装器只接受可识别的本产品目录和相同实例结构；不是任意版本迁移工具。
- 兼容性未验证或实例结构变化时，必须先设计迁移、回退与独立副本验证，不得强制覆盖。
- 保存旧版本不代表可随意只退程序；如新版本已产生数据，回退须依据完整备份和该次说明。
