# Batch 1A — 设计计划与实施门禁

状态：只完成设计工作；本文件不是 Runtime/Launcher/Setup 实施授权。

## 本轮设计步骤

1. 核对公开仓库工作区、分支、HEAD 和远端 main/tag；只读现有规划、公开 PROJECT 与安装/启动/依赖源码。
2. 按证据区分已具备能力、目标差距和待验证风险，参考 Node/npm 官方技术说明。
3. 比较私有 Runtime、SEA、Electron 和在线 bootstrap；形成 spec.md 推荐方案，不伪造用户技术选型确认。
4. 建立 L2 四文档，增量登记 Master Plan、Decisions、公开 PROJECT；运行文档链接、范围、敏感模式和 diff 检查。
5. 形成结果说明，停止于设计评审。

## 允许改动

- 本目录 intent.md、spec.md、plan.md、acceptance.md、RESULT.md。
- 上层 MASTER-PLAN.md、DECISIONS.md 的状态与入口。
- 公开根 PROJECT.md 的新阶段索引。

禁止修改业务代码、测试实现、脚本、依赖锁文件、工作流、版本字段和 Batch 0 基线记录。禁止安装、打包、启动服务、生成 Setup 或闭包；不读取任何运行实例。

## 后续实现准入草案（未批准、不执行）

- 先批准架构方向，再明确 Batch 1 后续实施范围，不以“设计验收”替代 Build 授权。
- 从公开源码允许清单设计新的 Runtime 构建/验证文件；保留 v1.0.0 原格式与原发行物。具体新增文件名在实施 Plan 决定，本轮不建空脚本。
- 先建立缺 Node/原生模块/资源/许可、锁文件冲突、路径逃逸、混入实例文件等失败反例，再实现构建工具。
- 在经批准的隔离 Windows x64 环境准备生产依赖；明确 npm 与原生 DLL 版本、源哈希和 license/NOTICE 来源。
- 核验最终包中全文件清单；在无系统 Node 和禁止下载条件下验证核心模块与 HTTP/页面功能，不使用真实业务数据。
- 闭包只作为后续 Launcher/Setup 输入，不绕过 Batch 2/3 提前建立新用户安装流程。
- 对比所有已有业务文件哈希；任何业务入口适配需要独立批准。

本轮只有文档草案，可按精确差异调整；不需要程序或数据回滚。不得删除历史记录或覆盖其他人的修改。仅文档设计不运行业务测试，不能报告运行闭包已通过。
