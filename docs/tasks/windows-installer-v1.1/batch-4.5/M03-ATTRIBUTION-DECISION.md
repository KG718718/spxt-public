# Batch 4.5 — M03真实对照观察目标决策卡

## 当前事实

Git控制面已恢复，M00/M01/M02历史事实不变。原T5的M03-T01—T08合成研究发现：同一PowerShell进程的整次`spawnSync.stderr`非空，不能说明字节来自显式Utility导入还是之后的`ConvertTo-Json`。T02/T03的不同内部来源可映射到相同汇总结果。相关49/49合成PASS是安全闭合测试，不是原M03两阶段分类门禁PASS。没有运行真实M03，唯一真实对照额度仍未使用；P02仍FAIL，生产不变。

## 技术约束

原批准要求同进程先确认导入阶段stderr为空，再只判断序列化阶段。现有汇总接口无法满足此阶段归因。跨两个OS管道的到达顺序或等待时间不能作为证明；未证明PowerShell流重定向或Console.SetError可完整捕获且不改变受验stderr。不得忽略stderr、放宽生产安全规则、追加Hosted或提前运行Final Full/QA。

## 可选方案及影响

**A｜建议：将唯一M03改为进程级非对称对照。** 同一进程显式导入Utility后执行旧M02等价序列化，只检查整次进程固定stdout和聚合stderr。聚合stderr为空可证明该次显式导入+序列化组合干净，支持“自动加载/首次解析参与触发”的假说，但仍非唯一根因；聚合stderr非空只能报`UNRESOLVED`，不得归因序列化，也不得改生产。先修订T02/T03合成语义、Master Review，然后至多一次真实Win10 M03，无Hosted。优点是低成本、保持原始stderr fail-closed；缺点是FAIL分支信息有限。这**改变原批准的阶段归因目标**，必须网页版明确同意。

**B｜保持原阶段归因目标。** 先设计并合成证明一个完整、不会掩盖或改变原始进程stderr的同进程阶段观察机制，再由Master Review决定是否能使用唯一真实M03。可能需要更复杂的同步或宿主级观测，时间与失真风险较高；本轮未获得可行证据，不应猜测可实现。

**C｜维持冻结。** 不追加诊断、生产修复或Hosted；等待其他环境/策略证据。

## 需要网页版决定

是否批准A的**进程级非对称判定**替代原M03的两阶段归因？若坚持原目标，请明确是否批准B的新增观察设计阶段；在其合成证明前仍不得真实运行。M03真实次数仍为0/1，Final Full0/1与QA0/1保持冻结。无论选项，任何生产修改及P01—P08/Full/QA须另有足够证据和授权。
