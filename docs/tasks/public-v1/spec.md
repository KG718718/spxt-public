## 员工替票授权：已获有条件确认（尚未实现）

2026-09-10用户确认：“不要和现在冲突，可以接受”。确认仅适用于下述授权配置方案；不是整份Spec/Plan批准，也不是“不存在回归”的测试结论。

### 来源代码事实

- `POST /api/users`由Admin创建账号，可同时建立员工收款对象；此操作不更新替票授权名单。
- `isAuthorizedReimburseName`仍读取写在代码中的固定名称集合。新安装者创建的新员工不因此自动拥有替票资格。
- `getInvoiceExpectedItems`优先读取已通过付款明细中的结构化收款对象类型：正式供应商与员工/公司收款对象分开判断，不以员工姓名认定正式供应商。
- `analyzeInvoiceCandidateForRows`同时核对所选明细类型与当前操作账号资格。现有Admin/审批岗在分析函数中有角色分支；不据此扩大其路由权限或新增审批能力。
- 历史缺结构化类型的明细、缺池类型的记录，也会调用上述固定名称判断。把该函数整体换成可变授权名单，可能使旧记录读取分类随授权变化；这是代码依赖所支持的风险，不是已复现的数据事故。

### 已确认的最小公开化方案

1. 复用现有用户管理中的有效员工列表，增加由Admin维护的“允许员工替票”勾选项；不手写授权用户名，不另建员工身份系统。
2. 新员工默认未授权；创建/关联员工收款对象不自动勾选。员工不能自行授权，审批岗不因此获得维护授权名单的权限。
3. 授权只影响该账号在原有项目/明细权限范围内的替票操作；不允许把正式供应商明细改用其他销售方，也不绕过购买方、日期、重复票号、金额占用和最终审核。
4. 账号身份按现有用户标识核对，不能拿供应商名称归一化或模糊匹配当作账号授权。停用、删除或撤销资格后，新提交与旧草稿递交均重新核对；授权变更留审计。
5. 权限与历史分类分别处理：授权变化不回写历史发票状态/金额，不改变已保存的收款对象或余票归属，不扩大跨员工余额使用范围。既有Admin/审批岗能力仍受原角色及路由约束。

说明性例子（虚构、未运行）：员工甲已建立关联收款对象，但尚未勾选替票资格，不能仅凭该关联使用销售方不同的替票；Admin授权后，也只能在本人原有可操作明细内、满足其他发票规则并经审核使用。

### 不冲突的实现与验收边界

仅用Admin配置取代固定名单作为操作账号资格来源，不扩展谁可以查看/操作哪个项目，不把员工收款关联等同于授权，不改变Admin/审批岗既有权限、正式供应商销售方校验、日期/票号/占用、余票可见与复用范围、历史状态或财务公式。

实现后必须用虚构账号与同一组受控输入对照：等价授权下原合法/非法业务结果一致；差异只限已确认的配置维护与授权变更。必须覆盖撤销授权、停用、旧草稿提交，以及历史发票/余票分类不变。无法满足时记录具体反例并返回用户，不以“公开化”为由静默改规则；未执行不得宣称已无冲突。
