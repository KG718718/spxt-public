## 员工替票授权：已获有条件确认（尚未实现）

2026-09-10用户确认：“不要和现在冲突，可以接受”。确认仅适用于下述授权配置方案；不是整份Spec/Plan批准，也不是“不存在回归”的测试结论。

### 来源代码事实

- `POST /api/users`由Admin创建账号，可同时建立员工收款对象；此操作不更新替票授权名单。
- `isAuthorizedReimburseName`仍读取写在代码中的固定名称集合。新安装者创建的新员工不因此自动拥有替票资格。
- `getInvoiceExpectedItems`优先读取已通过付款明细中的结构化收款对象类型：正式供应商与员工/公司收款对象分开判断，不以员工姓名认定正式供应商。
- `analyzeInvoiceCandidateForRows`同时核对所选明细类型与当前操作账号资格。现有Admin/审批岗在分析函数中有角色分支；不据此扩大其路由权限或新增审批能力。
- 历史缺结构化类型的明细、缺池类型的记录，也会调用上述固定名称判断。把该函数整体换成可变授权名单，可能使旧记录读取分类随授权变化；这是代码依赖所支持的风险，不是已复现的数据事故。

### 已确认的最小公开化方案

1. 复用现有用户管理中的有效员工列表，增加由Admin维护的“允许员工替票”勾选项；不手写授权用户名，不另建员工身份系统。
2. 新员工默认未授权；创建/关联员工收款对象不自动勾选。员工不能自行授权，审批岗不因此获得维护授权名单的权限。
3. 授权只影响该账号在原有项目/明细权限范围内的替票操作；不允许把正式供应商明细改用其他销售方，也不绕过购买方、日期、重复票号、金额占用和最终审核。
4. 账号身份按现有用户标识核对，不能拿供应商名称归一化或模糊匹配当作账号授权。停用、删除或撤销资格后，新提交与旧草稿递交均重新核对；授权变更留审计。
5. 权限与历史分类分别处理：授权变化不回写历史发票状态/金额，不改变已保存的收款对象或余票归属，不扩大跨员工余额使用范围。既有Admin/审批岗能力仍受原角色及路由约束。

说明性例子（虚构、未运行）：员工甲已建立关联收款对象，但尚未勾选替票资格，不能仅凭该关联使用销售方不同的替票；Admin授权后，也只能在本人原有可操作明细内、满足其他发票规则并经审核使用。

### 不冲突的实现与验收边界

仅用Admin配置取代固定名单作为操作账号资格来源，不扩展谁可以查看/操作哪个项目，不把员工收款关联等同于授权，不改变Admin/审批岗既有权限、正式供应商销售方校验、日期/票号/占用、余票可见与复用范围、历史状态或财务公式。

实现后必须用虚构账号与同一组受控输入对照：等价授权下原合法/非法业务结果一致；差异只限已确认的配置维护与授权变更。必须覆盖撤销授权、停用、旧草稿提交，以及历史发票/余票分类不变。无法满足时记录具体反例并返回用户，不以“公开化”为由静默改规则；未执行不得宣称已无冲突。

### 公司收款别名另行处理

源码的`supplierBankIsOptional`及`normalizeDebtCostPayeeItems`仍包含旧固定公司别名判断，分别影响银行信息可选性和欠款成本准入。不能仅替换显示文字，也不能未经确认扩大为所有公司收款对象自动享有同一资格。其公开化映射方式列为下一项待确认，本次员工授权建议不顺带批准；公司收款对象仍不是员工登录账号。

## 零业务数据交付（用户已确认，尚未封装验收）

本次“脱敏”的数据处理方式是不携带，而不是把真实名称、编号或金额改写后继续附带。生产安装包不包含原供应商、员工/公司收款对象或关联关系；也不自动生成同名替代对象、演示供应商或预置公司收款账号。

| 范围 | 新安装要求 |
|---|---|
| 登录账号及授权 | 预置账号为0，无原员工、测试账号或共享默认密码；首个Admin仅在使用者完成首次创建后产生 |
| 主数据 | 供应商、收款对象、甲方、员工关联及单位专用名单为空，由安装者自行维护 |
| 业务记录 | 项目、付款、欠款、发票、草稿、OCR业务任务、余票、奖金和月结记录均为空，不带旧统计汇总 |
| 业务文件及历史 | 不含原附件、上传缓存、导出文件、业务日志、历史备份、原邮件配置或发送记录 |
| 测试资料 | 合成夹具只用于隔离测试，不打入生产安装包，不在安装或首次启动时导入 |

保留程序、模块、字段结构和必要的基础类型。购买方等单位配置由Admin设置；公司专用参数不因空业务数据而自动变成通用默认值，其余公共默认值仍按未决规格确认。首次初始化产生的Admin及本次安装审计不是预置业务数据；初始化后业务表仍须为空。

零数据仅适用于全新安装。升级、重启、重装或已有数据损坏时，不得调用“恢复出厂/清空数据”冒充初始化，也不能用空库覆盖原库。不能因为数据文件未打包，就认为源码中的旧名称名单、公司别名和历史算例已被移除；这些仍按逐文件公开化边界处理。

## 局域网边界建议（待确认，未实测）

来源代码采用内存状态、文件持久化和主机侧解析，不能由此承诺多实例共享写入或每台员工电脑各装一套数据后自动同步。

- 建议一台主机运行一个服务并保存数据，员工和Admin通过各自浏览器访问同一实例；OCR只需安装在服务主机。
- 首次管理员初始化建议只允许主机本机执行，完成后关闭；不得为了让员工访问而向局域网开放未初始化的管理员创建入口。
- 默认本机访问；明确启用局域网后使用稳定主机地址，防火墙仅开放所需应用/端口及可信来源范围，不关闭防火墙，不开放公网或端口转发。[依据：Microsoft防火墙规则](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules)。
- 承载真实账号和业务数据的局域网访问建议采用HTTPS。现有HTTP实现不能冒充已加密；证书信任、访问地址、Cookie及代理边界需验证后才能承诺支持。[依据：OWASP TLS](https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html)。
- 邮件中的系统入口须指向使用者可访问的主机地址；OCR和邮件的安装/运行联网需求分别说明，不能把局域网访问等同于完全离线。
- 开发机不保存公开副本的边界不变。真实双机验收需以后指定独立测试主机和客户端并授权安装，不使用公司正式主机。
